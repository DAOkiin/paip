# Parsing / Scraping Pipelines — рабочий документ (v0.1)

Дата: 9 февраля 2026

## 1) Контекст и цель проекта

**Что вы делаете:** систему для сбора информации из интернета и других источников (сначала web, возможно RSS; позже — адаптеры для YouTube и “что угодно”), с последующей обработкой, поиском инсайтов и **синдикацией** (генерация статей, YouTube-контента и т.п.).

**Ключевые сценарии использования:**

- Сбор **новостей по интересующим темам**.
- Сбор и отслеживание **нарративов крипторынка**: появление новых трендов, изменения в трендах, динамика.
- Хранение данных так, чтобы можно было:
  - воспроизводимо обрабатывать,
  - сравнивать версии/изменения,
  - делать аналитику/поиск/агрегации,
  - генерировать производный контент.

## 2) Границы MVP (первый этап)

**В MVP:**

- Источники: **веб** (и потенциально RSS как “почти веб”).
- Подключение источников через **адаптеры/коннекторы** (единый интерфейс, разные реализации).
- Конвейер обработки: загрузка → извлечение текста/метаданных → NER/сигналы → определение трендов/нарративов → сохранение результатов.
- Хранение: сырые данные + нормализованные/обогащённые данные.
- Категоризация страниц (тип страницы в БД).

**После MVP (позже):**

- YouTube-адаптер и другие источники (Telegram и т.п.).
- Расширение таксономии/онтологии страниц и сущностей.
- Усложнение аналитики и контент-генерации.

## 3) Use cases (скелет для сегодняшнего описания)

Ниже — структура, которую можно прямо “раскрывать” в отдельные use case’ы.

### 3.1 Управление источниками

- Добавить источник (site/feed/список URL/шаблон).
- Настроить правила обхода (частота, ограничения, allow/deny, глубина, robots-политика).
- Включить/выключить источник, приоритизация.

### 3.2 Сбор данных (ingestion)

- Запланировать сбор по расписанию или по событию.
- Снять страницу (HTML + метаданные), при необходимости отрендерить (JS).
- Сохранить “сырой слепок” и технические метрики (статус, время, размер, ошибки).

### 3.3 Версионирование и изменения

- Хранить версии страницы (page snapshots).
- Выявлять изменения (diff по контенту / по ключевым блокам).
- Триггерить перерасчёт аналитики при значимых изменениях.

### 3.4 Извлечение контента

- Определить тип страницы (категория: статья/продукт/пост/главная/каталог/…).
- Извлечь текст, заголовок, автора, дату, теги, ссылки, медиа.
- Нормализовать (очистка, язык, дедупликация).

### 3.5 NLP / сигналинг

- NER (сущности: люди/компании/проекты/тикеры/гео/…).
- Ключевые фразы/темы, классификация по вашим “темам интереса”.
- Детект нарративов/трендов (рост упоминаний, новые связки сущностей, burst-сигналы).

### 3.6 Аналитика и выдача

- Поиск и фильтрация по источникам/датам/сущностям/темам.
- “Что изменилось?” по рынку/теме за период.
- Выгрузка дайджеста / отчёта.

### 3.7 Синдикация / генерация контента

- Сформировать “контент-пак” (цитаты, факты, графики/таблицы, ссылки на источники).
- Сгенерировать статью/скрипт видео/пост (с обязательной ссылочной базой).

## 4) Данные и БД: подход DDL-first + тестируемая модель

Вы отдельно подчёркивали: **не IDL, а DDL**, и желание *до кода* описать схему БД и сценарии запросов/вставок, чтобы тестировать модель.

### 4.1 Что хранить (минимальный набор сущностей)

- **sources**: источник, правила обхода, тип (web/rss), приоритет.
- **fetch\_jobs / runs**: задания и их результаты (статусы, тайминги, ошибки).
- **pages**: канонический URL, домен, текущая категория.
- **page\_snapshots**: версия контента (html/text, hash, retrieved\_at, headers).
- **extracted\_documents**: нормализованный текст + метаданные (title/date/author).
- **entities** + **document\_entities**: сущности и связи “документ-сущность”.
- **topics/narratives** + **signals**: нарративы, измерения/сигналы, временные ряды.
- (опционально) **users/subscriptions**: если планируются пользователи и подписки на темы/дайджесты.
- **generated\_artifacts**: “производный контент” и ссылки на источники.

### 4.2 Тестирование схемы и запросов

- Хранить DDL (миграции) + набор **“эталонных” insert/select** сценариев:
  - вставка источника,
  - вставка снапшота страницы,
  - извлечение сущностей,
  - построение агрегатов (тренды за период).
- Автотесты модели данных: поднимаем временную БД, накатываем DDL, прогоняем сценарии.

## 5) Архитектура (как вы её видите сейчас): event-driven scraping pipeline

То, что повторялось в запросах: **пайплайны**, **event-driven**, оркестрация (Temporal), адаптеры.

### 5.1 Компоненты верхнего уровня (для схемы сегодня)

- **Source Registry**: управление источниками и правилами.
- **Orchestrator / Workflow Engine (Temporal)**: управляет пайплайном, ретраями, состояниями, дедлайнами.
- **Ingestion Workers**:
  - Fetcher (HTTP) и/или Renderer (headless browser) для JS-сайтов.
  - Rate limit / politeness / прокси (при необходимости).
- **Content Extraction Service**: вытаскивает основной текст/метаданные, определяет тип страницы.
- **NLP / Enrichment Service**: NER, темы, сигналы.
- **Trends/Narratives Analytics**: расчёт трендов/изменений, временные ряды.
- **Storage Layer**:
  - Raw store (снапшоты),
  - Normalized store (документы/сущности/сигналы).
- **API / Query Layer**: поиск, фильтры, выдача отчётов/дайджестов.
- **Syndication / Content Generation**: сбор “контент-паков” и генерация материалов.
- **Observability**: логи/метрики/трейсы, алерты.

### 5.2 Поток данных (линейно)

1. Source → событие “нужно собрать”
2. Fetch/Render → raw snapshot
3. Extract → normalized document + category
4. Enrich (NER/Topics) → entities/signals
5. Analytics → narratives/trends
6. Serve/Generate → отчёты/контент

## Концепция системы

Система предназначена для автоматизированного сбора и обработки информации из интернет-источников, для которых реализованы соответствующие адаптеры. Каждый адаптер определяет способ подключения к источнику и формат извлекаемых данных.

Обработка информации выполняется с использованием настраиваемых пайплайнов, формируемых пользователем (человеком или агентом). Пайплайн представляет собой упорядоченную последовательность правил обработки данных, применяемых к входящим данным из источников.

Правила обработки являются частью системы и реализуются в виде расширяемых инструментов. Примеры правил включают извлечение контента, категоризацию, распознавание именованных сущностей (NER) и другие виды преобразований и анализа данных. Набор доступных правил не фиксирован и расширяется в процессе разработки в зависимости от решаемых задач.

Система не накладывает жёстких требований на семантику правил на раннем этапе, при этом предполагается, что правила используются как переиспользуемые компоненты пайплайнов и могут комбинироваться для решения различных кейсов.

Цель системы — обеспечить централизованный механизм мониторинга информации и структурированного хранения результатов обработки в форме, пригодной для последующего использования как человеком, так и программными агентами.

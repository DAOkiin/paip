- **PostgreSQL**

Temporal может хранить visibility в SQL/SQLite/Elasticsearch, но:

- **Advanced Visibility не поддерживается с Cassandra**.
- Для нагрузок “больше чем несколько workflow executions” Temporal **рекомендует Elasticsearch как visibility store**, потому что он лучше держит нагрузку и оптимизирует производительность. citeturn1view1

Практически: если ты хочешь нормальный поиск/фильтры по Search Attributes и масштабирование — планируй **Elasticsearch (или совместимый OpenSearch, если он у тебя стандарт де-факто, но совместимость версий надо сверять по docs для твоей версии Temporal)**.

## 3) Сеть и безопасность хоста

Temporal прямо говорит: **не выставлять Temporal hosts в публичный интернет**, относиться к Temporal Service как к критичному компоненту уровня БД, ограничивать сетевой доступ доверенными сетями. citeturn1view0

## 4) “Сервер” Temporal — это несколько сервисов, и требования зависят от масштаба

Temporal Server состоит из **4 независимо масштабируемых сервисов**: frontend, history, matching, worker. citeturn0search6\
Это важно: “системные требования” — не одна цифра, а **профиль ресурсов на каждый сервис + БД + visibility**.

## 5) Минимальные ресурсы: что можно считать “нижней границей”

Официальных “железных” цифр типа “минимум 4 CPU/16GB” в доке нет — потому что упирается в RPS/кол-во workflow/retention/размер историй.

Но как практический ориентир (особенно для Kubernetes), Temporal в гайде по K8s показывает пример ресурсов для **worker**-подов (не для server-подов!) порядка:

- limits: **0.5 CPU / 512Mi**
- requests: **0.2 CPU / 256Mi** citeturn1view2

Это не “официальный минимум для продакшена”, а пример стартовых значений — и на server-компоненты (history/matching/frontend) часто требуется больше, особенно history.

Для “локально попробовать” встречаются туториалы/чармы с минимумом уровня **2 CPU threads / 8GB RAM / 20GB disk** (как baseline для окружения), но это опять же про “поднять стенд”, а не про прод-нагрузку. citeturn0search19

## 6) Что чаще всего определяет требования (и где будет бутылочное горлышко)

1. **База данных** — главный потребитель ресурсов и самый частый bottleneck (CPU/IO/latency). Temporal активно пишет/читает историю, очереди, таймеры.
2. **History service** — обычно самый “тяжелый” по CPU/RAM внутри Temporal.
3. **Visibility store (Elasticsearch)** — отдельно по RAM/CPU/диску, зависит от объемов и запросов.
4. **Shard count** — влияет на параллелизм. Temporal рекомендует для small production **512 shards** (а не dev-дефолт 4). citeturn0search7

## 7) Как перевести это в “системные требования к серверу” в твоем случае

Если тебе нужно именно “что заказать/выделить” — правильнее считать **профиль развертывания**:

### A) Dev/PoC (1 нода, без HA)

- Temporal all-in-one + PostgreSQL (и опционально Elasticsearch)
- Цель: разработка, тест пайплайнов

### B) Small production (минимально жизнеспособный прод)

- Отдельно Temporal services (или хотя бы разнести DB отдельно)
- Управляемая PostgreSQL/MySQL + отдельный ES (или managed)
- Shards не dev-значение (ориентир 512+) citeturn0search7

### C) HA production

- Несколько реплик frontend/history/matching/worker, отдельные БД и ES кластера, мониторинг и лимиты

## 1) Базовые цифры latency внутри Temporal (без твоей бизнес-логики)

### Нижняя граница end-to-end latency

Temporal (Cloud) в статье прямо пишет, что **минимальная end-to-end latency workflow около \~100ms** (это про “интерактивные” сценарии, где важны миллисекунды). citeturn0search1

> Это не “всегда 100ms”, а “ниже этого почти не опустишься”, потому что есть сетевые round-trip’ы, запись состояния, диспатч задач и т.д.

### Ориентиры по API/Matching latency (p95)

В обсуждении метрик Temporal’а приводят практический ориентир:

- **Frontend API latency p95 желательно < 100ms**
- **Matching AddWorkflowTask \~ 50–100ms** citeturn0search26

Это полезно как “нормально/ненормально” для кластера.

### Пример измерений на 10/50/100 TPS (workflow с activity)

Есть реальный пример: workflow с 1 local activity + 3 activities, где **end-to-end latency на 10/50/100 TPS \~235–247ms в среднем**, p95 около 252–257ms. citeturn0search4\
Это уже “похоже на жизнь”: несколько activity, нагрузка до 100 TPS.

## 2) Пропускная способность (throughput): какие порядки вообще достижимы

Temporal масштабируется горизонтально, и реальная пропускная способность очень зависит от persistence (Cassandra/Postgres/MySQL), shard’ов и размера histories.

Из публичного опыта в прод/тестах:

- Есть кейс, где **кластер обрабатывает \~1500 flows/sec** на 6 узлах Cassandra и **\~4000 flows/sec** на 12 узлах Cassandra. citeturn0search14

А для *твоих точных цифр под твой пайплайн* правильный путь — прогонять бенчмарки на своём окружении:

- **maru** — официальный инструмент/репо для бенчмарков Temporal workflows (можно задавать сценарии “N workflows/sec X минут”). citeturn0search2
- **benchmark-latency** — репо Temporal для прогона latency-бенчей (намеренно “лёгкий” workload, чтобы мерить “встроенную” латентность). citeturn0search12

## 3) “Сложный пример” пайплайна твиттов: как получить *точные цифры* и что получится в расчёте

Возьмём типичный конвейер (упрощённо):

1. **Ingest**: сбор твиттов (API) батчами
2. **NER**: извлечение сущностей
3. **Trends**: агрегация/детект трендов по окнам
4. **Analytics**: расчёт метрик/запись в хранилище

### Как смоделировать в Temporal (важно для производительности)

Чтобы Temporal был быстрым, почти всегда делают:

- **батчирование** (например, 200–1000 твиттов на один workflow-run или на один activity-run)
- **идемпотентные activities**
- ограничение длины history (ContinueAsNew / периодические workflow) — иначе упрёшься в рост histories и БД

### Конкретный “сложный” сценарий для бенча (его реально прогнать maru)

**Workflows/sec:** 50 (стабильно)\
**Каждый workflow:**

- A1 FetchTweets (батч 500 твиттов) — 250ms (внешний API)
- A2 NER (500 твиттов) — 400ms (CPU/GPU сервис)
- A3 UpdateTrendWindow (агрегация) — 80ms
- A4 PersistAnalytics — 120ms\
  Параллельно: NER можно распараллелить на 5 чанков по 100 твиттов (5 activities), если нужно.

### Оценка времени одного workflow (приближённо, но с привязкой к измеренным overhead)

Если activities выполняются последовательно, “идеальная” сумма = 250 + 400 + 80 + 120 = **850ms**.

Добавим orchestration overhead Temporal:

- минимум порядка **\~100ms end-to-end нижней границы** (как “сквозная” добавка), citeturn0search1
- плюс возможные задержки на диспатч task’ов, которые в норме должны укладываться в десятки миллисекунд p95 по рекомендациям, citeturn0search26

Итого типично получишь **\~0.95–1.10s p50** на один такой workflow, если:

- воркеры не перегружены,
- Task Queues не в бэклоге,
- persistence latency нормальная.

Если же NER распараллелить на 5 чанков (5 activities параллельно по 100 твиттов) и каждый чанк 120ms, то NER-часть станет \~120–160ms (по медленнейшему), и workflow может упасть до **\~0.6–0.8s** (плюс те же накладные).

### Как получить “точные цифры”

Если тебе нужны *именно точные числа*, то правильный способ:

1. Поднять Temporal self-hosted (как у тебя планируется) с той же БД и теми же лимитами CPU.
2. Реализовать activities-заглушки с **реальным временем выполнения**, как у твоих сервисов (или подключить настоящие сервисы).
3. Прогнать:
   - **maru** для throughput и устойчивости на 10/50/100/500 workflows/sec citeturn0search2
   - **benchmark-latency** чтобы замерить “чистую” латентность оркестрации в твоей сети/инфре citeturn0search12

Если сравнивать **именно “метрики скорости”** (latency/throughput), то Temporal и Dagster живут в разных классах:

- **Temporal** — оркестрация *событий/задач* с низкой задержкой (десятки–сотни миллисекунд) и высокой частотой решений.
- **Dagster** — оркестрация *data runs / asset materializations*; задержка обычно определяется **тиканием daemon’ов, запуском run launcher (часто K8s Jobs) и временем выполнения шагов**, и это в норме секунды/минуты (а не миллисекунды).

## Temporal: задержка и пропускная способность (оркестрация)

**Минимальная end-to-end задержка**: Temporal прямо пишет, что *минимальная* end-to-end latency workflow порядка **\~100 ms** (для Temporal Cloud; в self-hosted будет зависеть от сети/DB, но порядок тот же). citeturn0search2

**Пример “сложнее пустышки”**: в обсуждении есть реальные замеры workflow с **1 local activity + 3 activities**:

- при 10 TPS avg \~247 ms, p95 \~258 ms
- при 50 TPS avg \~237 ms, p95 \~252 ms
- при 100 TPS avg \~235 ms, p95 \~254 ms citeturn0search18

**Бенч-инструменты**: maru (нагрузочные сценарии “N workflows/sec X минут”) citeturn0search6 и benchmark-latency (легкий workload, чтобы мерить “встроенную” латентность) citeturn0search10.

## Dagster: “скорость” на практике (тики, сенсоры, запуск runs)

У Dagster нет “официальной метрики” вида “минимальная задержка DAG = 100ms”, потому что обычно измеряют не это, а **время запуска/выполнения run’ов, работу scheduler/sensor daemon’ов и очередей**.

### 1) Daemon-тики и сенсоры — это не миллисекунды

- Dagster официально упоминает, что **дефолтный timeout сенсора — 60 секунд** (и сенсоры могут в него упираться). citeturn0search9
- В реальном кейсе масштабирования у пользователя **schedule tick evaluation** занимал **\~40 секунд в лучшем случае**, а при нагрузке доходил до **10–15 минут на один тик**. citeturn0search1

Это важная “метрика скорости”: если ты пытаешься делать *near-real-time orchestration* (каждые секунды/десятки секунд), Dagster может стать узким местом именно на уровне tick evaluation и очередей.

### 2) Запуск run’ов зависит от run launcher (часто K8s Jobs/Celery)

Dagster описывает, что **run launcher** — это слой, который реально поднимает вычисления для runs. citeturn0search11\
В варианте Celery+Kubernetes запуск/исполнение включает **run worker job**, постановку шагов в Celery и **step execution jobs** в Kubernetes. Это по определению добавляет оверхед (минимум на создание/старт job/pod). citeturn0search31

А в прод-обсуждениях встречаются проблемы, когда runs “долго dequeue’ятся” (вплоть до часов) при определённых условиях нагрузки/конфигурации. citeturn0search27

## Что это значит для твоего “Twitter → NER → тренды → аналитика” примера

### Если тебе нужно *потоково и быстро* (секунды и меньше)

**Temporal** обычно проще довести до режима:

- “каждый батч/сообщение = workflow или activity”
- задержки оркестрации порядка **\~0.1–0.3s** + время твоих сервисов (API/NER/аналитика) citeturn0search2turn0search18

### Если тебе ок *батчево/окнами* (минуты)

**Dagster** силён, когда:

- ты работаешь окнами (1–5–15 минут, часы)
- важны lineage, assets, материализации, backfills
- “запуск чуть позже” (секунды/минуты) не ломает продукт

Но для “near-real-time” у Dagster чаще упираешься не в скорость выполнения твоего NER, а в:

- schedule/sensor tick evaluation (вплоть до десятков секунд и хуже) citeturn0search1turn0search9
- run launching overhead (особенно K8s jobs) citeturn0search11turn0search31

## Практическое правило выбора по “скорости”

- **Temporal**: когда нужна *низкая латентность оркестрации*, много мелких событий/тасок, динамическая ветвистость.
- **Dagster**: когда важнее *data model/asset graph*, повторяемость, backfill, observability, а единица работы — “run”, и нормальная гранулярность — минуты+.

Если скажешь целевую гранулярность (например, “обновлять тренды каждые 10 секунд” vs “каждые 5 минут”) и ожидаемый поток (твиты/сек), я сразу переведу это в “какие задержки реалистичны” для обоих подходов и где будут узкие места.

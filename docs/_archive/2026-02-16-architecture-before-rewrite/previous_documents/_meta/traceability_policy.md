# Политика трассируемости требований

## Принцип

Требования прослеживаются сверху вниз:

- `docs/product/*` — намерения и реальная ценность для пользователя.
- `iterations/<итерация>/selected_requirements.md` — выбранные для реализации требования.
- `iterations/<итерация>/architecture.md`, `domain_model.md`, `event_model.md`, `data_model.md` — проектные решения.
- `iterations/<итерация>/acceptance.md` — проверочные условия и критерии.

Нельзя закрыть фичу без явной связи хотя бы к одному `AC-XXX`.

## Матрица трассируемости

Для каждой итерации ведётся `traceability.md` в формате:

- `US-XXX` / `UC-XXX` / `NFR-XXX`
- `Requirement Decision` — выбрано в итерацию или отложено
- `Design artifacts` — ссылки на архитектурные документы
- `Test/verification` — где проверяется (AC/ручной сценарий/интеграционный тест)
- `Owner` — ответственный
- `Status` — planned / in progress / blocked / done

## Регламент обновления

- При изменении содержания пользовательской истории: обновить ID only if сущность изменилась; иначе `Update`.
- При добавлении сценария в итерацию: добавить его в `selected_requirements` и в `traceability`.
- При переносе в следующий спринт: закрыть `Status`, зафиксировать причину и перенести ссылку в `open_questions.md` или `risks`.
- При появлении критичного дефекта, связанного с требованием: добавить связанное `RISK-XXX` или AC с флагом `blocked`.

# Система документации PAIP

Документация организована по `внутренней SDLC` цепочке:

- **Research → Product → Iteration → Ops → Archive**
- Каждый документ имеет одну роль и одну ответственную зону (кто владеет обновлением).
- Исходный смысл проекта описан в `product/global_vision.md`; далее документами уточняется, что из этого реально делаем и в какой последовательности.

## Уровни системы

- `docs/product` — продуктовое мышление и поведение системы глазами пользователя.
- `docs/research` — сырые идеи, источники, гипотезы, решения, эксперименты.
- `docs/iterations` — рабочие артефакты конкретной итерации (scope, проектные решения, план, приемка, трассируемость).
- `docs/ops` — эксплуатационные артефакты (установка, runbooks, наблюдаемость).
- `docs/_meta` — метадокументы системы: правила именования, трассируемость, шаблоны.
- `docs/_archive` — исторические артефакты без текущего применения.
- `docs/_meta/documentation_structure.md` — полный каталог и назначение каждого документа.

## Базовые правила

- Все продуктовые истории (`user story`) и `use case` — на русском, без тех. деталей.
- Технические модели (domain/events/data architecture) — в итерационном наборе и должны ссылаться на продуктовые истории.
- Любое решение фиксируется через документ:
  - если это вопрос **что делать**, его кладём в `product`;
  - если **как это сделать технически**, в `iterations/<итерация>/...`.
- Каждая итерация имеет фиксированный список обязательных артефактов (`scope`, `selected_requirements`, `traceability`, `plan`, `acceptance`).

## Читаемый порядок

1. `product/global_vision.md`  
2. `product/global_user_stories.md` + `product/global_use_cases.md`  
3. `iterations/current.md`  
4. Артефакты текущей итерации (`scope`, `selected_requirements`, `traceability`, `architecture`, `acceptance`)  
5. `ops/` (после появления runnable-пайплайна)

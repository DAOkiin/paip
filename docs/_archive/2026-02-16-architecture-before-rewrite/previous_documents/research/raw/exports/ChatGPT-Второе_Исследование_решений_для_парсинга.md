## Scrapy (Python)

**Описание:**  Scrapy – популярный фреймворк для веб-скрейпинга и веб-краулинга на Python. Проект с открытым исходным кодом (лицензия BSD) поддерживается компанией Zyte (ранее Scrapinghub)【32†L153-L161】. Архитектура построена вокруг «спайдеров» – самостоятельных модулей-краулеров, которым задаются инструкции для обхода сайтов【32†L158-L166】. Scrapy позволяет извлекать структурированные данные из веб-страниц, а также через API, и обрабатывать их в конвейере (pipelines). Данные могут автоматически сохраняться в файлы (JSON, CSV, XML и др.) или базу данных через механизмы feed exports и item pipelines.

**Особенности архитектуры:** за подключение новых источников отвечают классы *Spider*, которые можно писать для каждого сайта или API. Поддерживается широкий набор middlewares и расширений для обработки HTTP-запросов, очередей, автотроттлинга и др. Спайдеры генерируют объекты данных (*Items*), которые проходят через *pipeline* – настраиваемую цепочку шагов (очистка, преобразование, сохранение). Такой дизайн облегчает повторное использование кода и масштабирование парсинга【32†L158-L166】.

**Плюсы:** высокая производительность при краулинге; активное сообщество и регулярные обновления (последний релиз 2025 года【32†L139-L147】); гибкость за счёт middlewares/pipelines; совместимость с различными хранилищами через экспорт данных.\
**Минусы:** сфокусирован на веб-страницах – для других источников (например, Telegram) требуется писать кастомные пауки или использовать API вручную; отсутствует встроенный планировщик задач/DAG – для регулярного запуска скрейперов нужно интегрировать с внешними оркестраторами (например, Airflow) или сервисами (Scrapyd и пр.).

**GitHub:** [scrapy/scrapy](https://github.com/scrapy/scrapy) (★ 47k+). Лицензия BSD-3-Clause, допускается коммерческое использование.

## Apache Airflow (Python)

**Описание:** Apache Airflow – открытая платформа оркестрации workflows, написанная на Python и развиваемая Apache Software Foundation【23†L1-L8】. Позволяет програмmatically определять, планировать и мониторить сложные пайплайны данных в виде DAG (ориентированных ацикличных графов). Широко применяется для ETL/ELT, тасков машинного обучения, периодического сбора данных и др.

**Особенности архитектуры:** пользователи определяют *DAG*-граф, где узлы – это задачи (*Operators*) на Python (или вызывающие внешние системы), а рёбра задают зависимости и порядок выполнения. Airflow обладает модульной архитектурой через систему провайдеров: существуют десятки готовых операторов/хуков для подключения к БД, облачным хранилищам, REST API и другим сервисам. Например, есть HttpOperator для вызова веб-API, SSHOperator, различные Sensors для отслеживания событий и т.д. Новые интеграции можно добавлять, создавая собственные операторы или плагины【22†L5-L13】. Пайплайн выполняется согласно расписанию (Scheduler) или по внешнему триггеру. Имеется веб-интерфейс для мониторинга выполнения.

**Плюсы:** мощный оркестратор с поддержкой сложных зависимостей; большая библиотека готовых коннекторов/операторов для внешних систем; активное сообщество (20k+ звёзд, >1000 контрибьюторов) и регулярные обновления; масштабируемость – может работать распределённо на кластере. Лицензия Apache 2.0 (полностью открыта для коммерческого использования)【23†L1-L8】.\
**Минусы:** сам по себе не выполняет “парсинг” – необходимо писать код задач (например, использовать библиотеки вроде Requests/Feedparser для RSS или Telegram API внутри задачи Airflow); требователен к ресурсам при развёртывании (необходимы службы scheduler, executor, база для метаданных); для простых сценариев избыточен по сложности.

**GitHub:** [apache/airflow](https://github.com/apache/airflow) (★ 32k+). Лицензия Apache-2.0.

## Apache NiFi (Java)

**Описание:** Apache NiFi – мощный инструмент для автоматизации потока данных между системами, ориентированный на визуальное программирование потоков. Предоставляет веб-интерфейс, где конвейер сборки/обработки данных строится из коробочных процессоров, соединённых линиями (потоковая модель)【1†L113-L122】【25†L264-L272】. NiFi поддерживает как потоковый, так и пакетный режим, позволяя в реальном времени собирать и перерабатывать большие объёмы данных из разнообразных источников. Проект Apache, лицензия Apache 2.0【25†L254-L262】.

**Особенности архитектуры:**  NiFi имеет **богатый набор встроенных адаптеров** (процессоров) для десятков источников и приемников данных【1†L121-L124】. Например, из коробки доступны процессоры для HTTP(S) запросов, чтения RSS/Atom-фидов, получения сообщений из Kafka/MQ, доступа к файловой системе, JDBC-базам, облачным сервисам и др. Для новых источников можно написать пользовательский процессор на Java или сценарий (NiFi поддерживает запуск скриптов, в т.ч. Jython, Groovy). Сами данные в потоке представлены в виде FlowFiles, к которым применяются последовательно операции (парсинг, преобразование, маршрутизация). Поддерживается концепция очередей с обратным давлением (back pressure) и гарантированная доставка данных【25†L269-L277】. NiFi позволяет визуально отслеживать прогресс и состояние потоков, а при сбоях – автоматизировать обработку ошибок, перезапуск и т.д.【25†L266-L275】.

**Плюсы:** **простой no-code/low-code интерфейс** – разработка пайплайна перетаскиванием блоков; множество готовых коннекторов для интеграции (HTTP, файлы, БД, MQTT, etc.) без программирования【1†L121-L124】; поддерживает как непрерывный стриминг, так и периодический ETL; горизонтально масштабируется (кластер NiFi) для высоких нагрузок; активный Apache-проект с сообществом (5k+ звёзд на GitHub)【25†L258-L266】.\
**Минусы:** требует Java-окружение, развёртывание на сервере; высокая нагрузка на память при больших потоках данных; для сложной логики может потребоваться писать собственные процессоры (Java/Scala), что повышает порог входа; отсутствует продвинутое управление сложными зависимостями задач (в отличие от Airflow DAG) – модель больше потоковая, чем оркестровая.

**GitHub:** [apache/nifi](https://github.com/apache/nifi) (★ 6k). Лицензия Apache-2.0.

## Apache Camel (Java)

**Описание:** Apache Camel – библиотека интеграции, реализующая паттерны Enterprise Integration Patterns (EIP) для маршрутизации и преобразования сообщений. Это **“конструктор” интеграций**: с его помощью разработчики могут программно связать любые источники и приёмники данных, описав правила маршрутизации в видеDSL на Java или XML. Camel не предоставляет GUI, но является крайне гибким фреймворком для создания собственных коннекторов и интеграционных сервисов. Лицензия Apache 2.0【15†L797-L805】.

**Особенности архитектуры:** Camel обладает **богатой экосистемой компонентов** (более 300) для подключения практически к любому протоколу или системе【15†L797-L805】. Компоненты существуют для HTTP/REST, файлов, БД (JDBC, JPA), очередей (JMS, Kafka), облачных сервисов (AWS, Google), соцсетей и мессенджеров. В частности, имеется компонент **Camel-Telegram** для работы с Telegram Bot API (отправка и получение сообщений ботом)【11†L1-L7】, компонент **Camel-RSS/Atom** для опроса RSS-лент【29†L5-L13】, и многие другие. Архитектура позволяет добавлять новые компоненты (адаптеры) посредством реализации соответствующих интерфейсов. Маршруты Camel представляют собой потоковую цепочку обработки: сообщение из источника проходит через серию *Processor* или *Bean*, где может трансформироваться (например, из XML в JSON), фильтроваться, мультикаситься на несколько получателей и т.д. Camel может работать встроенно (embedding) в приложении или как самостоятельный сервис (напр. в контейнере Spring Boot или Quarkus).

**Плюсы:** одна из самых зрелых интеграционных технологий; **500+ готовых коннекторов** ко всему – от FTP и почты до Telegram и Salesforce【15†L797-L805】【11†L1-L7】; гибкость маршрутов – любые произвольные логические условия, трансформации; активное сообщество Apache с постоянным развитием (актуальная версия Camel 3.x); Apache-лицензия позволяет свободно использовать в коммерческих продуктах.\
**Минусы:** требует знания Java/EIP – сравнительно крутой вход для Python-разработчиков; отсутствие интерфейса – конфигурирование через код или XML; запуск Camel-виртуальной машины добавляет оверхед (хотя есть лёгкие варианты – Camel K, Quarkus); для оркестрации сложных разнородных задач (DAG) Camel не предназначен – это скорее ESB/маршрутизатор.

**GitHub:** [apache/camel](https://github.com/apache/camel) (★ 6k+). Лицензия Apache-2.0.

## Node-RED (Node.js)

**Описание:** Node-RED – популярный инструмент визуального *low-code* программирования потоков данных, изначально разработанный IBM для IoT, теперь проект OpenJS Foundation. Позволяет через веб-интерфейс **соединять “узлы” (nodes)**, представляющие собой разные действия или интеграции, в единый поток выполнения. Node-RED особенно широко применяется в IoT и автоматизации, но также пригоден для общих задач интеграции (в том числе парсинга данных из веб-API, RSS и т.п.). Распространяется под лицензией Apache 2.0【20†L147-L155】 (подходит для коммерческого применения).

**Особенности архитектуры:** Node-RED имеет модульную систему *nodes* (аналог плагинов). Сообщество создало **более 4000 готовых коннекторов** для самых разных источников и протоколов【20†L201-L209】. Например, доступны узлы для HTTP-запросов, для MQTT, для разных баз данных, электронных почт, соцсетей. Существует несколько пакетов узлов для Telegram – как через Bot API, так и через клиент MTProto【28†L1-L9】. Для RSS-лент можно использовать HTTP-запрос + узел парсинга XML (или установить специализированный узел). Узлы можно комбинировать: напр., узел-подписчик на RSS выдаёт новые элементы, которые передаются на узел обработки (фильтрации) и затем на узел отправки сообщений в Telegram – **всё это настраивается без написания кода**. Под капотом Node-RED работает на Node.js, а потоки представляют собой JSON-конфигурации. Возможно расширение – написание своих узлов на JavaScript при необходимости.

**Плюсы:** крайне низкий порог входа – интуитивно понятный графический редактор потоков; огромный выбор готовых интеграций (тысячи узлов) благодаря открытому сообществу【20†L201-L209】; поддержка событийной модели (flows запускаются по приходе сообщений или по расписанию); легковесность – можно запускать на Raspberry Pi и небольших серверах; Apache-лицензия, активно поддерживается (релизы в 2025 году, проект зрелый с 2013).\
**Минусы:** Node.js-экосистема – не Python (интеграция с Python возможна через REST/HTTP взаимодействие или вызов скриптов, но это дополнительная прослойка); для очень больших и критичных пайплайнов может быть сложнее отлаживать или масштабировать (отсутствует встроенная кластеризация, хотя потоки можно распределять вручную); лицензия Apache позволяет коммерческое использование, однако если нужна полная кастомизация UI или multi-user, может потребоваться сторонний управляющий слой (например, FlowFuse).

**GitHub:** [node-red/node-red](https://github.com/node-red/node-red) (★ 17k). Лицензия Apache-2.0.

## n8n (Node.js)

**Описание:** n8n – платформa автоматизации workflow, аналогичная Node-RED по концепции, но ориентированная на интеграцию веб-сервисов и SaaS-приложений. Предоставляет **web-интерфейс для сборки workflow** из блоков-интеграций (nodes), может запускать цепочки как по расписанию, так и реагируя на триггеры (входящее событие). Имеет \~400 встроенных интеграций (коннекторов) и активно развивается сообществом и одноимённой компанией【30†L5-L13】. Код n8n открыт (*source-available*) под собственными лицензиями (Sustainable Use License для сообщества) – бесплатен для личного и коммерческого использования, если не предоставлять n8n как публичный SaaS-сервис【17†L13-L21】【17†L23-L31】.

**Особенности архитектуры:** n8n написан на Node.js/TypeScript. Интеграции реализованы как *nodes*, которые можно настраивать (вводить ключи API, параметры) прямо в UI. Поддерживаются популярные источники: например, есть узлы **Telegram** (триггер на новое сообщение или отправка сообщения), узлы для HTTP-запросов, для чтения RSS (можно парсить RSS через HTTP + XML-ноду), интеграции с Google Sheets, Slack, GitHub и сотнями других сервисов. Расширяемость обеспечивается плагинной архитектурой: можно писать новые узлы на JavaScript, используя SDK. Пайплайн исполняется внутри n8n runtime; возможно self-hosted развёртывание в Docker. Для данных, требующих временного хранения между шагами, доступны встроенные средства (например, передача данных между узлами, или интеграция с внешними БД через узлы).

**Плюсы:** современный удобный интерфейс; большое количество готовых коннекторов (400+ интеграций) из коробки【30†L5-L13】; сочетание подходов no-code и возможностей кода (можно вставлять произвольный JavaScript для расширенной логики); активное развитие – проект крайне популярен (75k+ звёзд на GitHub в 2025) и имеет оживлённое сообщество. Лицензия позволяет бесплатное внутреннее использование в компаниях【17†L23-L31】.\
**Минусы:** лицензия *fair-code* не является классической OSS (исходники открыты, но есть ограничения на предоставление как облачного сервиса); основан на Node.js – для интенсивной работы с данными может уступать по производительности сугубо Python-решениям; для сложных трансформаций данных иногда удобнее написать скрипт, чем конфигурировать множество узлов. Тем не менее n8n интегрируется с Python-кодом через API или запуск скриптов, если необходимо.

**GitHub:** [n8n-io/n8n](https://github.com/n8n-io/n8n) (★ 100k). Лицензия Sustainable Use License (ограниченно open-source, но бесплатна для коммерческого использования в своих проектах).

## Airbyte (Java/Python)

**Описание:** Airbyte – современная open-source платформа для конвейеров переноса данных (ELT). Отличается моделью «коннекторы как плагины»: имеется сотни готовых коннекторов для источников и приёмников данных, а также возможность быстро создавать новые через шаблоны. Airbyte позволяет синхронизировать данные из разнообразных систем (API, базы, приложения) в целевые хранилища (data warehouse, data lake) с минимальными усилиями【25†L192-L200】. Основной сервер Airbyte написан на Java, коннекторы реализуются в виде Docker-контейнеров (часто на Python, с использованием SDK Singer/Airbyte). Лицензия: части проекта под MIT, а ядро – под Elastic License v2【25†L182-L190】 (бесплатно для собственного использования, ограничивает создание облачных SaaS-клонов).

**Особенности архитектуры:** Архитектура Airbyte модульная: **коннекторы разделяются на источники и приёмники**. Каждый коннектор – изолированный Docker с кодом, реализующим стандартный интерфейс (чтение или запись данных пакетами). Имеется **500+ готовых коннекторов** (API популярных SaaS, баз данных, файловых хранилищ и т.д.)【25†L192-L200】. Например, доступны коннекторы для Facebook Ads, Stripe, MySQL, Google Sheets и сотен других. В случае отсутствия готового можно использовать генератор (low-code UI) либо писать на Python по спецификации. Airbyte оркестрирует запуск коннекторов: по расписанию или вручную запускается “Источник”, который выгружает данные (в формате JSON-стрим), и тут же передаёт их в коннектор-“Приёмник” для загрузки в конечную систему. Поддерживается **инкрементальная загрузка** (CDC) для многих источников, автоматическая схемная эволюция. Airbyte предоставляет веб-интерфейс для настройки коннекторов, мониторинга синхронизаций и управления ошибками.

**Плюсы:** огромная база готовых интеграций (поддерживаются **сотни источников** данных)【25†L192-L200】; единообразный подход к разным видам источников через протокол Airbyte; активное развитие (16k+ звёзд, >1000 контрибьюторов)【25†L186-L194】 и коммерческая поддержка, но при этом открыт исходный код; гибкое развёртывание – можно запускать локально в Docker, в Kubernetes, в облаке и пр.; коннекторы обычно имеют свободную лицензию (MIT), что удобно для доработки под себя.\
**Минусы:** относительно тяжёлый стек (требуется Java-сервер + Docker для каждого коннектора); не рассчитан на real-time потоковые данные – обычно выполняет периодические батч-выгрузки; для нестандартных источников (например, парсинг произвольных веб-страниц или Telegram-чатов) отсутствуют готовые коннекторы – придётся писать свой (что возможно, но требует изучить протокол); ядро под Elastic License v2 – для внутреннего использования это бесплатно, однако юридически это не OSS по OSI (впрочем, для большинства коммерческих сценариев ограничений нет).

**GitHub:** [airbytehq/airbyte](https://github.com/airbytehq/airbyte) (★ 20k). Лицензия MIT (коннекторы) / Elastic v2 (ядро).

## Singer + Meltano (Python)

**Описание:** **Singer** – это открытый стандарт и экосистема коннекторов для переноса данных. Коннекторы Singer разделяются на **“taps”** (источники, извлекающие данные) и **“targets”** (приёмники, загружающие данные). Каждый *tap/target* – это отдельный CLI-инструмент (чаще Python-скрипт), обменивающийся данными через стандартные JSON-сообщения【21†L130-L138】. Singer изначально разработан компанией Stitch Data и передан сообществу; лицензии коннекторов в основном MIT/Apache. **Meltano** – оркестрационная платформа (развивается компанией GitLab), которая использует коннекторы Singer для построения полноценных ELT-пайплайнов. Meltano упрощает установку, комбинирование и планирование выполнения множества tap/target, а также интегрирует инструменты трансформации (например, dbt). Проекты Singer/Meltano полностью открыты (MIT-лицензия для Meltano【25†L330-L338】) и пригодны для коммерческого использования.

**Особенности архитектуры:** Коннекторы Singer максимально унифицированы: каждый **tap** подключается к своему источнику (БД, API, файл), читает данные и выводит поток JSON-сообщений со **стандартом Singer** (включающим данные и метаданные схемы)【21†L130-L138】. Существуют готовые *taps* практически для любых популярных источников – от PostgreSQL и Salesforce до Facebook Ads. Сообщество поддерживает **300+ коннекторов Singer**【27†L109-L117】, объединённых в Meltano Hub (крупнейший каталог открытых коннекторов в мире на 2021 г.)【27†L109-L117】. Аналогично, *targets* позволяют загрузить данные в десятки систем – SQL-хранилища, файлы, Elastic, etc. Meltano действует как каркас: конфигурации tap/target описываются в `meltano.yml`, и Meltano может запускать их последовательно, управлять параметрами, выполнять тесты коннекторов【27†L97-L105】. Meltano также добавляет возможности оркестрации (планирование по расписанию, запуск потоков, отслеживание) и расширения пайплайна шагами трансформации (связка с dbt для SQL-преобразований). Архитектура Meltano плагинная – помимо Singer-коннекторов, можно подключать плагины для других инструментов.

**Плюсы:** большой выбор готовых коннекторов Singer (более **300 источников/приёмников** на Meltano Hub)【27†L109-L117】, многие из которых активно поддерживаются сообществом; стандартизованный протокол – легко комбинировать любые источник и приёмник; Meltano предоставляет удобный CLI и UI для управления конвейером, логирования, тестирования коннекторов; полностью открытый код (MIT)【25†L330-L338】, можно модифицировать под свои нужды; подходит для корпоративного использования – нет ограничений по лицензии.\
**Минусы:** развёртывание менее интегрированное, чем в Airbyte – коннекторы Singer запускаются как отдельные процессы, их нужно координировать (в этом помогает Meltano, но порог освоения есть); не реалтайм – рассчитано на batch-выгрузки; качество коннекторов варьируется (часть написана сообществом и может требовать доработок или обновления API); Meltano пока относительно молодой проект (≈1k звёзд)【25†L333-L341】, сообщество меньше, чем у Airbyte, хотя растёт.

**GitHub:** [singer-io](https://github.com/singer-io) (каталог репозиториев коннекторов Singer), [meltano/meltano](https://github.com/meltano/meltano) (★ 1.4k). Оба под лицензией MIT.

## DLT (Data Loading Tool, Python)

**Описание:** **dlt** – современная open-source библиотека на Python для создания пайплайнов загрузки данных с упором на простоту и **декларативный подход**【25†L302-L310】. Проект развивается сообществом DLT Hub. Dlt позволяет с минимальным кодом извлекать данные из различных источников (в т.ч. через REST API) и загружать в хранилища (базы данных, data lakes, озёра) с поддержкой схемной эволюции и инкрементальных обновлений. Лицензия Apache 2.0【25†L292-L300】 – полностью открыто для коммерческого применения.

**Особенности архитектуры:** Dlt задуман как легковесная библиотека без тяжелой инфраструктуры – **пишете Python-скрипт** и запускаете его где угодно (локально, в Airflow, в AWS Lambda и т.д.)【9†L47-L55】. Библиотека предоставляет набор готовых модулей-источников (*sources*), а также API для описания своих. Уже доступно **60+ готовых источников** – от любых SQL/NoSQL баз до Google Sheets, Salesforce и других SaaS【9†L68-L76】. Можно генерировать код коннектора из OpenAPI-спецификации автоматически. Dlt управляет схемой данных: умеет автоматически выводить схему, отслеживать изменения (Schema Evolution) и применять их к целевому хранилищу. Поддерживается **incremental loading/CDC** – коннекторы могут брать только новые записи с момента последней загрузки【25†L304-L313】. Dlt обеспечивает транзакционность загрузки, контроль за дубликатами, ведение истории изменений (SCD2) и пр. Пайплайн в dlt описывается декларативно: разработчик определяет функции-источники (генерирующие стрим данных) и указывает целевое хранилище – далее библиотека сама проходит по данным, буферизует и записывает. Dlt интегрируется с популярными хранилищами (BigQuery, Snowflake, Postgres и др.), поддерживает запись в форматы (Parquet, Delta Lake...).

**Плюсы:** минимальный “центр тяжести” – простой Python-пакет, не требующий отдельных сервисов; возможность запускать где угодно (от ноутбука до облачных функций)【9†L47-L55】; есть **десятки встроенных коннекторов** + удобный механизм написания новых (в том числе универсальный REST API коннектор)【9†L79-L87】; встроенная поддержка инкрементальных обновлений и нармализации данных из коробки【25†L302-L310】【25†L304-L313】; активное развитие (≈5k звёзд, >160 контрибьюторов на GitHub)【9†L26-L34】, сообщество растёт; лицензия Apache 2.0.\
**Минусы:** проект появился недавно (активно развивается с \~2022) – ещё не такой зрелый, как Airbyte или Singer, поэтому число коннекторов пока меньше (**\~60 источников** на конец 2025)【9†L68-L76】; отсутствует собственный UI – конфигурация через код/конфиг-файлы (хотя это упрощает встраивание в существующие пайплайны); для постоянного расписания задач понадобится внешняя оркестрация (например, запуск dlt-скриптов через cron, Airflow или Prefect); специфика лицензии отсутствует (классический Apache 2.0).

**GitHub:** [dlt-hub/dlt](https://github.com/dlt-hub/dlt) (★ 5k). Лицензия Apache-2.0.

## Что можно подтвердить из публичных источников

### 1) Бэкенд для продуктовых API

- В вакансиях OpenAI прямо пишут, что их backend stack включает **Python, FastAPI, Postgres**. citeturn1view3

Это не говорит “всё на FastAPI”, но подтверждает: **Python/FastAPI — часть продакшн-бэкенда**, а **Postgres — ключевое хранилище**.

### 2) Инфраструктура и “платформенный” слой

- В другой вакансии (Real Time) OpenAI перечисляет инфраструктурный стек: **Kubernetes, Go, Python, Terraform, Kafka, Postgres, Snowflake**. citeturn1view2\
  Это очень показательно: **Kafka** — почти всегда основа для асинхронной событийной шины/очередей, **Kubernetes** — запуск сервисов/воркеров/джобов, **Go+Python** — микросервисы и обработчики.

- OpenAI публиковали инженерный пост о том, как они масштабировали **Kubernetes** (до 7,500 узлов) — подтверждает, что Kubernetes является их крупной продакшн-инфрой (хотя пост про ML-инфру, а не про весь бэкенд). citeturn1view1

### 3) PostgreSQL как “сердце” части продакшена

- В январе 2026 OpenAI опубликовали подробный пост: **PostgreSQL — критическая система под капотом, powering core products like ChatGPT and OpenAI’s API**, и они масштабировали её до миллионов QPS, с **одним primary + \~50 read replicas** по регионам. citeturn1view0\
  Это важно для асинхронности тоже: такой Postgres почти наверняка хранит **состояние** (аккаунты/лимиты/метаданные/запросы/кеш-ключи/идемпотентность/аудит) вокруг синхронных и фоновых процессов.

### 4) Durable workflows / долгоживущие задачи

- Temporal (компания) в своём блоге описывает интеграцию **OpenAI Agents SDK + Temporal**, где оркестрация идёт через **Temporal Workflows**, а “каждый agent invocation” выполняется как **Temporal Activity**. citeturn1view5\
  Это **не 100% доказательство**, что “весь OpenAI на Temporal”, но это сильный сигнал: **Temporal у них используется как минимум в контексте агентных/долгих процессов** (а Temporal как раз про надёжную асинхронную оркестрацию: ретраи, идемпотентность, восстановление).

### 5) Потоковая асинхронность (stream processing)

- Есть сторонний разбор, который утверждает, что OpenAI рассказывали на конференции Current 2025 про использование **Kafka + Flink/PyFlink** для real-time streaming платформы; в статье есть ссылки на записи сессий. Это **вторичный источник**, но он согласуется с тем, что Kafka официально фигурирует в их вакансии. citeturn1view4turn1view2

## Как это обычно раскладывается по “типам асинхронности” у компаний такого масштаба

Если собрать подтверждённые куски в разумную архитектурную картину:

1. **Синхронный слой (API request/response)**
   - Python **FastAPI** сервисы, которые принимают запросы, валидируют, пишут состояние в **Postgres**, ставят события/джобы, отдают ответ. citeturn1view3turn1view0

2. **Очереди/события и воркеры**
   - **Kafka** как транспорт событий/буфер между сервисами и асинхронными потребителями (воркерами). citeturn1view2
   - Воркеры на **Go/Python**, запущенные в **Kubernetes**.

3. **Долгие/надёжные workflow**
   - **Temporal** (по крайней мере для агентных/долгих оркестраций) — когда нужен “durable execution” и гарантии восстановления. citeturn1view5

4. **Стриминг/near-real-time обработки**
   - Kafka + (возможный) Flink/PyFlink для потоковых пайплайнов. citeturn1view4turn1view2

### 1) Data Model Spec

### 2) DDL как исходник истины

**Артефакт:** `/db/ddl/*.sql` (или один `schema.sql`)
Что должно быть внутри DDL:

- `CREATE TABLE ...` по подсхемам
- ограничения: `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`
- индексы: `CREATE INDEX ...`
- базовые перечисления/типы (если нужно)
- (опционально) материализованные представления/вьюхи для “типовых запросов”

Ключевой принцип: **DDL — это “контракт”**, на который опираются тесты.

---

### 3) Набор “типовых запросов” (DML/queries) до кода

**Артефакт:** `/db/queries/*.sql`
Ты хочешь заранее иметь “вставки, запросы, подобные истории”. Значит мы фиксируем:

- `insert_user.sql`, `create_task.sql`, `schedule_task.sql`
- `create_run.sql`, `finish_run.sql`, `save_raw_item.sql`
- `upsert_normalized_entity.sql` (или аналог)
- `find_new_items_since_last_run.sql`
- `dedup_candidates.sql`
- `rule_evaluation_inputs.sql`
- `create_notification.sql`, `list_notifications.sql`

Важно: это **не “реализация сервиса”**, а библиотека SQL-контрактов: “как система будет пользоваться БД”.

- минимальные наборы данных для сценариев тестирования

### 5) SQL-level тесты модели данных

**Артефакт:** `/db/tests/*.sql` + тест-раннер (пока без продуктового кода)
Тесты делятся на 3 слоя:

1. **DDL-инварианты**

- таблицы создаются
- constraint’ы работают (нельзя вставить кривые данные)
- каскады/ссылочная целостность как ожидается

2. **Сценарные тесты (Given/When/Then)**
   Примеры сценариев, ровно как ты описал:

- Given user, When create task, Then task exists and принадлежит user
- Given task, When create run + insert raw items, Then raw items привязаны к run
- Given два источника с одинаковым событием, When normalize, Then одна нормализованная сущность + две связи источников (дедуп)

3. **Тесты “типовых запросов”**

- каждый запрос из `/db/queries` имеет тест:
  - корректные результаты
  - корректное поведение при пустых данных
  - корректное поведение при повторном вызове (идемпотентность где нужно)

## 1) База: “как устроен crawler внутри” (фундаментальные компоненты)

Эти материалы полезны, чтобы **правильно “нарезать” доменную модель/состояния/таблицы** ещё до выбора конкретного стека.

### Mercator (классическая архитектура масштабируемого crawler)

- Описывает пайплайн “worker → fetch → process → extract links → URL-seen test → add to frontier” и то, какие структуры данных реально нужны (frontier, URL-seen/content-seen, processing modules). citeturn23view0
- Важное для проектирования: **URL frontier** не просто FIFO: из-за “politeness” (не держать много одновременных запросов к одному хосту) frontier реализуют как набор очередей/подочередей и распределяют URL по хосту так, чтобы один сервер не долбили параллельно разные воркеры. citeturn23view0
- Там же: “URL-seen test” и обсуждение компромиссов (точные структуры vs Bloom filter и т.п.) — это напрямую влияет на твои таблицы/индексы/уникальность. citeturn23view0

### Heritrix (архивный crawler, полезен как “reference model”)

- Документация показывает, что пайплайн часто оформляют как **processor chains** (Candidate/Fetch/Disposition) и что мониторинг/репорты строятся вокруг того, сколько URI прошло через какие процессоры. citeturn14view0
- Важно для “event thinking”: у Heritrix есть механика “action directory” и “recovery journal”, то есть система рассчитана на **воспроизводимость состояния и восстановление очередей** после сбоев. citeturn14view0

### Incremental crawling с Heritrix (про re-crawl/revisit, состояние и next fetch)

- Хорошо проясняет два ключевых места в архитектуре:
  1. **Frontier** как “плагин, который хранит состояние crawl”
  2. **цепочка процессоров**, где каждый делает дискретный шаг (fetch, link extraction, write to disk). citeturn11view2
- Для DDL/модели данных это особенно важно, если ты планируешь **переобход**, “next\_fetch\_at”, “change detection”, разные политики по типам ресурсов. citeturn11view2

## 2) Event-driven/open-source архитектуры “как оно делается вживую”

Это прямые примеры, где pipeline строится вокруг **streams/topics** и где удобно подсмотреть, **какие “ивенты” и какие роли процессов** обычно выделяют.

### Frontera (Kafka-based distributed crawl frontier) — эталон для event-driven crawling

- Документация даёт чёткую модель: в distributed-режиме есть **message bus**, а система — “замкнутый цикл” демонов:
  - **Spiders/Fetchers** (скачивание + извлечение ссылок/данных)
  - **Strategy workers** (скоринг ссылок, решение “что и когда качать”, остановка)
  - **DB workers** (хранение метаданных/контента/score, генерация новых батчей для скачивания). citeturn25view0
- Там же важное: “politeness by design” — каждый хост скачивается **не более чем одним spider-процессом** через **stream partitioning**. Это прямое архитектурное следствие для твоей модели “очередей по хосту/шардинга”. citeturn25view0
- Плюс: стратегия может меняться “на лету” без остановки crawl — это аргумент в пользу явной **event-модели и версионирования**. citeturn25view0

**Кластерный гайд Frontera** полезен как список того, что реально “решают до старта”:\*\*

- Kafka “recommended” как message bus (ZeroMQ упоминается как менее надёжный вариант). citeturn19view0
- Явно перечислены Kafka-топики/стримы: **spider log / spider feed / scoring log** и рекомендации по partitions. citeturn19view0
- Прямо написано, что компоненты можно рестартить “без major data loss” — то есть дизайн рассчитан на **повторяемость/идемпотентность обработки сообщений**. citeturn19view0

### Scrapy Cluster (Redis + Kafka) — “on-demand scraping cluster”

- Формулировка прямо в доках: **distributed on demand scraping cluster** на Redis и Kafka. citeturn20view0
- Важно: вход и выход — **Kafka topics**; seed URLs распределяются между множеством “ожидающих” spider-инстансов, координация запросов — через Redis. citeturn20view0
- Очень конкретная “event surface”: один входной топик (`demo.incoming`) и два выходных (`demo.outbound_firehose` для action-ивентов и `demo.crawled_firehose` для HTML crawl results). citeturn20view0
- Подсказка для твоей event-модели: они сразу разделяют “команды/управление” и “результаты crawl” по разным топикам. citeturn20view0

### StormCrawler (Apache Storm topology) — streaming crawler с низкой латентностью

- Хорош как пример “стримингового” пайплайна: spouts/bolts/streams. citeturn24view0
- Важнейшее: **FetcherBolt** держит внутренние очереди по IP/domain/hostname, выставляет delay и уважает robots.txt — то есть “politeness” реализован не абстрактно, а структурно. citeturn24view0
- Есть понятие **status stream** для статусов/ошибок и обновления информации о URL (DISCOVERED/FETCHED/FETCH\_ERROR/…). citeturn24view0
- В “basic scenario” прямо упоминается, что source может быть очередью типа RabbitMQ/AWS SQS и т.д. — то есть это хорошо ложится на event-driven мышление. citeturn24view0

### Crawlee (JS/TS, Playwright/Puppeteer) — современный стек под динамические сайты

Это не “архитектура пайплайна” в смысле распределённой системы, но полезно как **референс того, какие abstractions удобны на уровне рантайма**:

- В статье выделяют: autoscaling (`AutoscaledPool`), “request storage” (Request Queue/List) и “results storage” (Datasets/Key-Value Stores) — хороший словарь для доменной модели. citeturn21view0

## 3) Cloud reference architectures: event-driven пайплайны на управляемых сервисах

Очень полезный материал именно про **event-driven decomposed crawler**:

- Прямо раскладывает типовой алгоритм crawler вокруг **очереди URL** и предлагает разбить его на шаги, оркестрируемые Step Functions, чтобы обойти лимит Lambda 15 минут. citeturn10view0

- Параллелизм через Map state — с явным предупреждением не DDOS-ить сайт (batching). citeturn10view0

### Google Cloud: Cloud Run + Pub/Sub

- Тут не “про скрейпинг”, но это каноничный building block: сервис в Cloud Run вызывается **push subscription из Pub/Sub**, т.е. классический event-driven consumer. citeturn17view0

### Общие best practices по event-driven (полезно именно для твоей event-модели/контрактов)

- AWS прямо фиксирует: EDA обычно состоит из **producer → message broker → consumer**, а также что producer владеет **event schema и semantics** (как контрактом), и отдельно подчёркивает тему дублей/ошибок доставки. citeturn16view0
- Док по Lambda хорошо объясняет “push vs pull”, роль SQS как буфера между сервисами и то, что очереди/брокеры помогают decouple и переживать пики/ретраи (и где появляются trade-offs вроде eventual consistency и дублей). citeturn16view1

### Azure: Web-Queue-Worker style (как универсальная схема “front → queue → worker”)

- Классика: front-end пишет в БД/ставит задания в очередь, worker обрабатывает “долго/тяжело” асинхронно; оба компонента stateless, масштабируются независимо; воркер может запускаться сообщениями очереди или по расписанию. citeturn17view1
- Очень полезное предупреждение для проектирования DDL/тестов: возможна проблема консистентности “записали в БД, но не отправили сообщение в очередь”, и как направление решения упоминается Transactional Outbox. citeturn17view1

- Это ровно тот дизайн, который облегчает тестирование модели данных: сырые артефакты неизменяемы, а “результаты парсинга” — производные, пересчитываемые. citeturn18view0

## 5) Что “повторяется” почти везде (и значит, это стоит заранее зафиксировать в документации/DDL)

Не добавляю “левую фантазию”, а формулирую то, что явно видно по нескольким архитектурам выше:

1. **URL frontier / очередь задач** — почти всегда отдельная сущность/подсистема
   - Mercator: frontier + URL-seen + politeness через разбиение очередей по хосту/воркеру. citeturn23view0
   - Frontera: spider feed/log/scoring + partitioning по хосту. citeturn25view0turn19view0
   - AWS (serverless crawler): очередь URL должна переживать шаги → выносят в DynamoDB. citeturn10view0

2. **Состояние URL/ресурса** (discovered/fetched/error/next\_fetch\_at/…) — не “деталь реализации”, а часть модели
   - StormCrawler: status stream и перечисление статусов. citeturn24view0
   - Heritrix: отчёты по frontier/очередям/dup-by-hash и т.д. citeturn14view0
   - Heritrix incremental: явно про “frontier maintains state”, per-host queues, “time of next processing”. citeturn11view2

3. **Контракты событий и владение схемами**
   - В Frontera и Scrapy Cluster топики/стримы — это фактически API системы (кто что публикует/читает). citeturn25view0turn20view0
   - AWS best practices по EDA подчёркивают критичность схемы/семантики событий как единственного контракта producer↔consumer. citeturn16view0

4. **Повторная обработка и сбои** — архитектуры обычно подразумевают, что ретраи/дубли возможны
   - Step Functions / Lambda docs прямо про retries/ошибки/дубли и про то, что очередь (SQS/таблица/лог) — “elastic buffer”. citeturn10view0turn16view1
   - Frontera кластер-гайд говорит о перезапуске компонентов без большой потери данных — это подразумевает “правильные” семантики обработки сообщений/состояния. citeturn19view0

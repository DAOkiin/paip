# 01. Vision & MVP Scope

> Этот документ — контракт на MVP: что делаем, что не делаем, и какие решения уже зафиксированы.
> Полный north star / философия / “куда это может вырасти” — в `global_vision.md`.

## Название

PAIP — Personal AI Pipeline (рабочее: Universal Data Ingestion & Synthesis Platform)

## Зачем

Автоматизировать рутину мониторинга информации: сбор новостей, обнаружение нового, уведомления. Всё, что сейчас делается руками и теряется в шуме.

## Outcome (MVP)

[Decision] Работающая система, которая по расписанию собирает данные из настроенного источника, находит новое (без дублей) и присылает дайджест в Telegram.

## MVP Wedge (первый сквозной сценарий)

[Decision] Один минимальный сценарий, который “прокалывает” всю систему от конфигурации до результата:

- пользователь добавляет монитор “новости по запросу” (SearXNG query);
- по расписанию запускается сбор;
- результаты нормализуются и дедуплицируются;
- определяется “что нового” относительно уже виденного пользователем;
- формируется короткий дайджест и отправляется в Telegram.

Если этот wedge работает, остальной MVP превращается в добавление ещё источников и правил по тому же контуру.

## Метрики успеха MVP

[Decision]
- End-to-end: “добавил монитор → получил дайджест” без ручных шагов.
- Дедупликация: одна и та же ссылка/документ не приходит повторно одному и тому же монитору.
- Latency: от появления результата в источнике до сообщения ≤ 30 минут (при polling).
- Отладочность: для каждого сообщения можно понять “почему оно пришло” (лог + сохранённое сырьё).

## Scope

### IN (MVP, Decision)

- SearXNG adapter (поиск новостей по запросу) как первый источник.
- Периодический сбор (polling) через Temporal Schedules.
- PostgreSQL как единое хранилище (SoR).
- Сохранение сырого результата + нормализация в единый формат `RawDocument`/`Document`.
- Exact dedup (минимально достаточный) + “unseen” по monitor_id.
- Telegram-бот как основной UI (минимум команд для добавить/посмотреть/запустить).
- Docker Compose для локального деплоя.

### Stretch (Hypothesis)

- Website adapter (aiohttp + CSS selectors; Playwright только если необходимо).
- Twitter adapter (или замена на RSS/Nitter, если упираемся в API/лимиты).
- Near-duplicate dedup (simhash) и/или LLM fallback на сложных кейсах.
- Отслеживание цен (snapshot → diff → alert) как отдельный wedge после новостей.
- Минимальный FastAPI CRUD, если Telegram-команд окажется недостаточно.

### OUT (осознанно не делаем в MVP, Decision)

- Web UI / дашборд (кроме минимальных текстовых интерфейсов).
- Граф знаний / NER / тематическая классификация как обязательная часть MVP.
- Генерация контента (статьи, видео-скрипты).
- Тренд-аналитика и “нарративы”.
- Multi-tenancy / авторизация.
- Горизонтальное масштабирование (Kafka, кластерный Temporal).
- Production deployment / CI/CD.

## Инварианты (Decision)

- Temporal — оркестратор; PostgreSQL — source of truth.
- Сырые данные сохраняются (чтобы можно было воспроизвести и отладить пайплайн).
- Pipeline шаги идемпотентны и безопасны к ретраям.
- В MVP — polling, а не streaming/real-time.
- MVP — монолит с модулями, без микросервисной “инфры ради инфры”.

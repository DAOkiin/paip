# SDLC

## Термины и определения

| Термин                           | Определение                                                                                                                            |
|----------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| SDLC                             | Рабочий цикл разработки: от формулировки проблемы и требований до проверки результата и фиксации выводов релиза.                       |
| Артефакт                         | Любой управляемый документ процесса (например: `scope`, `selected_requirements`, `architecture`, `acceptance`, `traceability`, `ADR`). |
| Global-слой                      | Долгоживущий слой документации проекта: цели, потребности, глобальные требования и общая терминология.                                 |
| Iteration-слой                   | Слой конкретной итерации/релиза: что делаем сейчас, как проектируем, как проверяем и что выпустили.                                    |
| Scope итерации                   | Явно зафиксированные границы итерации (`IN/OUT`) и критерии успеха для текущего шага.                                                  |
| Design input                     | Входной артефакт проектирования в итерации (например: `scope`, `selected_requirements`, выбранные `OUT`).                              |
| Design output                    | Выходной артефакт проектирования в итерации (например: `architecture`, `domain_model`, `event_model`, `data_model`, `ADR`).            |
| Requirement (`US`/`UC`/`NFR`)    | Требование к продукту или системе: пользовательские истории (`US`), use cases (`UC`) и нефункциональные требования (`NFR`).            |
| Job (`JOB`, AJTBD)               | Пользовательская задача-прогресс, ради которой существует продуктовый сценарий.                                                        |
| Job map                          | Карта этапов выполнения `Job`, используемая для выявления проблем и проектирования улучшений.                                          |
| Forces of progress               | Факторы, которые двигают или тормозят выполнение `Job` и принятие решения пользователем (мотивация, страхи, инерция).                  |
| Outcome (`OUT`)                  | Желаемый измеримый результат выполнения `Job`, который используется для выбора требований и оценки прогресса.                          |
| Hypothesis (`HYP`)               | Проверяемое предположение о том, что конкретное решение или изменение улучшит `Outcome`.                                               |
| Evidence (`EVD`)                 | Источник фактов (исследование, данные, наблюдения), на который опираются `HYP`, требования и архитектурные решения.                    |
| ADR                              | Architecture Decision Record: отдельный зафиксированный документ архитектурного решения с контекстом и компромиссами.                  |
| Acceptance criterion (`AC`/`AT`) | Проверяемый критерий/сценарий приемки, подтверждающий выполнение выбранного требования в рамках итерации.                              |
| Трассируемость                   | Явные связи между `EVD -> JOB/OUT -> US/UC/NFR -> ADR -> AC/AT -> release learnings`.                                                  |
| Матрица трассируемости           | Табличная форма трассируемости для итерации, где фиксируются связи требований, решений, приемки и статусов.                            |
| Review gate                      | Контрольная точка проверки качества артефактов (перед baseline, планированием или релизом).                                            |
| Baseline                         | Зафиксированная версия набора артефактов итерации, от которой ведутся разработка, review и изменения.                                  |
| Release learnings                | Пост-релизные выводы: что сработало/не сработало по `OUT/HYP/ADR` и что меняем в следующей итерации.                                   |
